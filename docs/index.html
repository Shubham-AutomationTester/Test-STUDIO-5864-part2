Execution guide

Use the repository README and qa/TEST-PLAN.md for the full runbook.

01 / PUBLISH

Render: full HTTP-header coverage

  1. Upload the entire extracted repository, including docs/ and render.yaml, to GitHub.
  2. In Render, use New > Blueprint and connect the repository. A plain Static Site setup does not automatically import the Blueprint header rules.
  3. The publish directory is ./docs. There is no runtime server and no install step.
  4. Verify the final GET headers. Do not add a catch-all rewrite to index.html.
02 / ALTERNATIVES

Netlify, GitHub Pages and local preview

Netlify: deploy with the included netlify.toml, publishing docs/. Manual file upload: upload the contents of docs/, including _headers.

GitHub Pages: publish main /docs. Custom HTTP headers are not provided by these files on GitHub Pages. Project-site robots tests also require rules at the host-root /robots.txt.

python3 tools/serve.py --port 8000

Localhost is for local fixture checks. A hosted SearchStax crawler cannot reach your laptop's localhost.

03 / CONFIGURE CRAWL

Prevent accidental discovery

Use a dedicated QA app/index and a fresh crawl queue. Copy a suite seed. Include both /suites/ and /cases/ beneath your site prefix; depth at least 5 and item budget at least 500.

Do not scope only to the suite directory. Disable sitemap discovery, imports and other start URLs. Exclude the operator dashboard, assets and 404 page. Wait for all earlier runs to finish before resetting state.

Run the core suites with Ignore robots.txt OFF and ON. Use fresh state between independent runs; preserve the index only for lifecycle tests.

04 / IDENTITY

Confirm the supported bot token

A full HTTP User-Agent string is not automatically the robots meta-name token. Confirm the mapping with engineering or the implementation, then rebuild:

python3 tools/build.py --bot-name CONFIRMED_TOKEN \
  --confirm-bot-token

Deploy regenerated files and host rules. Do not grade matching-bot cases while the token is only a placeholder.

05 / OBSERVE

Measure different pipeline outcomes

noindex: parent can be fetched/processed but cannot add or update its document. Its ordinary child remains eligible.

nofollow: parent can index; no child may be enqueued from its links. A separate permitted occurrence can still enqueue the same target.

Record app ID, crawl definition/run IDs, timestamps, actual User-Agent, response headers, queue provenance and Solr/index document evidence. Do not infer queue behavior only from search-preview absence.

06 / SAME-URL UPDATES

Use the lifecycle phases

python3 tools/build.py --phase baseline
python3 tools/build.py --phase restricted
python3 tools/build.py --phase restored

These are three separate deploy-and-crawl steps, not commands to run back-to-back. Keep the same parent URL and existing index. Force a real re-fetch after each deployment.

U01/U02 prohibit a V2 update under noindex. Retention versus deletion of V1 is not defined by the ticket. U03/U04 introduce a previously undiscovered child to avoid stale-queue false failures.

!
Do not turn assumptions into release-blocking defects.

The ticket is the acceptance contract. Google behavior is useful background, not a substitute for SearchStax-specific precedence.
